# API Gateway


Шлюз стоит перед тремя внутренними сервисами (`users`, `orders`, `payments`), которые наружу не смотрят. Весь трафик проходит через шлюз. Один из сервисов (`orders`) периодически деградирует, что не должно затрагивать остальные маршруты.

**Стек:** Python 3.14.7, FastAPI, httpx, Pydantic v2, SQLAlchemy, PostgreSQL, Redis, pytest, Locust, Docker Compose.

---

## 1. Запуск

Через Docker и Docker Compose:

```bash
cp .env.example .env
docker compose up --build
```

Одна команда поднимает:

- `postgres` и `redis`;
- три заглушки `users`, `orders`, `payments`;
- `gateway` на порту `8080`.

Миграция и сиды применяются автоматически при старте `gateway` через `scripts/entrypoint.sh`.

Проверка:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/api/users/me
```

Маршрутизация:

| Путь шлюза | Назначение |
|---|---|
| `/api/users/*` | `http://users:8000/*` |
| `/api/orders/*` | `http://orders:8000/*` |
| `/api/payments/*` | `http://payments:8000/*` |

## 2. Тесты

Тесты запускаются одной командой и работают с реальными PostgreSQL и Redis из того же compose:

```bash
docker compose --profile test up --build --abort-on-container-exit --exit-code-from tests
```

Если шлюз уже запущен через `docker compose up`, тесты можно прогнать прямо в его контейнере:

```bash
docker compose exec \
  -e GATEWAY_URL=http://localhost:8080 \
  -e ORDERS_INTERNAL_URL=http://orders:8000 \
  -e DATABASE_URL=postgresql+asyncpg://gateway:gateway@postgres:5432/gateway \
  -e REDIS_URL=redis://redis:6379/0 \
  gateway pytest -v
```

Покрытие:

- юнит-тесты политики повторов: идемпотентные методы повторяются, `POST` не повторяется никогда, таймаут чтения не повторяется;
- интеграционные тесты: проброс и возврат `correlation_id`, проксирование с записью аудита в PostgreSQL, отсутствие дублирования `POST` при таймауте и при `503`;
- отдельно проверяется, что `POST` не дублируется ни при каких обстоятельствах.

## 3. Нагрузка

Нагрузочный тест находится в `load/` и запускается одной командой:

```bash
docker compose --profile load run --rm load
```

`load/run_load.sh` выполняет три шага:

1. `baseline` — 300 пользователей, около 300 RPS, 30 секунд, равномерно по трём маршрутам;
2. деградация `orders` до 10 секунд;
3. `degraded` — те же 300 RPS, 60 секунд, на фоне медленного `orders`.

Результаты складываются в `load/results/*.csv`.

Перед замером аудит отключается через `AUDIT_ENABLED=false`, чтобы синхронная запись в PostgreSQL не искажала латентность. В тестах аудит включён — это переопределяет `docker-compose.test.yml`.

## 4. Структура проекта

```text
gateway/
  main.py          # FastAPI-приложение, middleware, exception handlers
  config.py        # настройки через pydantic-settings (.env)
  proxy.py         # ядро: таймауты, повторы, бюджет времени
  limiter.py       # asyncio.Semaphore на каждый сервис
  circuit.py       # circuit breaker на Redis
  db.py            # модель аудита (SQLAlchemy)
  context.py       # ContextVar для correlation_id
downstream/
  stub.py          # заглушка сервиса: задержка, код ответа, вероятность ошибки
scripts/
  migrate.py       # SQL-миграция, создаёт таблицу аудита
  seed.py          # наполнение БД
  entrypoint.sh    # миграция, сид, старт
load/
  locustfile.py    # профиль нагрузки
  run_load.sh      # baseline -> деградация -> degraded
tests/             # юнит и интеграционные тесты
```

## 5. Принятые решения и их обоснавания

### Один общий `httpx.AsyncClient`

Используется один клиент на всё приложение с явными лимитами пула `max_connections` и `max_keepalive_connections`.



### Таймауты и бюджет времени

Для каждого маршрута отдельно задаются:

- `connect_timeout`;
- `read_timeout`;
- `total_timeout` — общий бюджет времени на запрос.

Реализация — `httpx.Timeout` плюс `asyncio.wait_for` на общий бюджет. При превышении возвращается `504` в едином формате:

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "request_id": "..."
  }
}
```

### Повторы

Повторяются только идемпотентные методы:

- `GET`;
- `HEAD`;
- `OPTIONS`;
- `PUT`;
- `DELETE`.

Повторы выполняются только при:

- ошибках соединения;
- таймаутах соединения;
- ответах `503`.

`POST` не повторяется никогда.

Между попытками выдерживается небольшая пауза. Общее число попыток ограничено бюджетом времени, чтобы повторы не растягивали запрос бесконечно.

### Изоляция сервисов через `asyncio.Semaphore`

Чтобы медленный сервис не исчерпывал ресурсы шлюза, для каждого маршрута используется отдельный семафор с лимитом `max_concurrency`.

Если свободных слотов нет, запрос ждёт не дольше `LIMITER_TIMEOUT_MS`, после чего получает `503`. Это реализует сброс нагрузки при переполнении очереди.

### `correlation_id`

Идентификатор запроса берётся из заголовка `X-Request-Id`. Если заголовка нет, генерируется `uuid4`.

Значение помещается в `ContextVar`, передаётся в сервис и возвращается клиенту в ответе. Это также позволяет писать его в логи без сквозного проброса через все функции.

### Простая SQL-миграция вместо Alembic

Таблица одна, поэтому выбран идемпотентный скрипт `scripts/migrate.py` с `CREATE TABLE IF NOT EXISTS`, который применяется при старте.

Alembic рассматривался как стандарт для растущей схемы, но для одной таблицы он избыточен. При росте схемы предполагается переход на Alembic.

### Аудит в PostgreSQL

Запись аудита выполняется синхронно — ради простоты и надёжности.

Известная цена решения: запись в БД добавляет латентность. Поэтому во время нагрузки аудит отключается.

Для продакшена предполагается вынос записи в фоновую очередь с батчингом, чтобы аудит не влиял на путь запроса.

### Circuit breaker на Redis

Реализован минимальный вариант:

- ошибки считаются в Redis;
- при превышении порога цепь открывается;
- запросы к больному сервису быстро получают `503`.

При недоступности Redis шлюз не падает и продолжает пропускать трафик. Это сознательный выбор в пользу доступности.

Известное упрощение: отсутствует состояние `half-open` с квотой пробных запросов.

### Нагрузка: Locust

Locust выбран как часть общего Python-стека.

Рассматривался k6 как более удобный инструмент для постоянного RPS, но отклонён ради единого рантайма и скорости интеграции.

## 6. Методика замеров

Соблюдены условия корректного замера.

### Прогрев

У Locust есть ramp-up: 50 пользователей в секунду до 300, около 6 секунд. Дополнительно весь 30-секундный baseline служит прогревом перед сценарием деградации.

### Перцентили вместо среднего

Используются `p95` и `p99` из отчёта Locust, а не среднее значение.

### База наполнена

При старте выполняется `scripts/seed.py`.

### Сервис запущен без `--reload`

Используется:

```bash
uvicorn gateway.main:app --host 0.0.0.0 --port 8080 --workers 1
```

Флаг `--reload` не используется.

### Генератор нагрузки

Генератор запущен в отдельном контейнере, но на том же хосте, что и шлюз.

Оговорка: в идеале генератор нагрузки должен находиться на отдельной машине, чтобы не конкурировать за CPU и сеть со шлюзом.

В данном прогоне Locust стабильно держал около 300 RPS без само-троттлинга, поэтому влиянием можно пренебречь, но факт фиксируется.

## 7. Результаты замеров

### Условия

- Железо: MacBook Air M4, ram 16
- Лимит памяти контейнера: около 7.7 GiB.
- Число воркеров шлюза: 1.
- Нагрузка: 300 пользователей, около 300 RPS, равномерно по трём маршрутам.
- Длительность: 30 секунд baseline и 60 секунд во время деградации.
- Аудит на время нагрузки отключён.

### До деградации, 30 секунд

| Маршрут | Метод | p50 | p95 | p99 | Ошибки |
|---|---|---:|---:|---:|---:|
| `/api/users` | GET | 320 ms | 360 ms | 380 ms | 0% |
| `/api/orders` | POST | 320 ms | 370 ms | 380 ms | 0% |
| `/api/payments` | GET | 320 ms | 370 ms | 380 ms | 0% |

### Во время деградации `orders`, 60 секунд

| Маршрут | Метод | p50 | p95 | p99 | Ошибки |
|---|---|---:|---:|---:|---:|
| `/api/users` | GET | 89 ms | 240 ms | 300 ms | 0% |
| `/api/orders` | POST | 75 ms | 1000 ms | 1200 ms | 100% |
| `/api/payments` | GET | 90 ms | 230 ms | 300 ms | 0% |

### Память и соединения шлюза во время деградации

| Метрика | Значение | Источник |
|---|---:|---|
| Память контейнера | 84.46 MiB | `docker stats` |
| CPU | 0.26% | `docker stats` |
| Строки в `/proc/net/tcp` и `/proc/net/tcp6` | 2592 | `cat /proc/net/tcp /proc/net/tcp6 | wc -l` |

Оговорка: число из `/proc/net/tcp` включает состояния вроде `TIME_WAIT`, поэтому это верхняя оценка, а не только активные соединения.

### Ошибки `orders` во время деградации

| Код | Количество | Причина |
|---|---:|---|
| `503` | 3751 | не хватило слота в семафоре, запрос сброшен быстро |
| `504` | 2066 | слот был занят, но запрос упёрся в `total_timeout=1s` |

### Вывод по критерию приёмки

Требование задания:

> Маршруты `users` и `payments` продолжают отвечать с `p95` не хуже, чем в полтора раза от нормы.

Расчёт:

- норма `p95` для `users` в baseline: 360 ms;
- допустимый порог: `360 * 1.5 = 540 ms`;
- фактический `p95` во время деградации: 240 ms.

Для `payments`:

- норма `p95`: 370 ms;
- допустимый порог: `370 * 1.5 = 555 ms`;
- фактический `p95` во время деградации: 230 ms.

Запас выдержан более чем в два раза. Деградация `orders` не затронула `users` и `payments`.

## 8. Важный нюанс

Основное узкое место — семафор `orders` с лимитом `max_concurrency=100`.

Подтверждение:

1. В `orders` приходит около 100 RPS.
2. При времени ответа 10 секунд по закону Литтла потребовалось бы около 1000 одновременных запросов.
3. Семафор разрешает только 100 одновременных запросов.
4. Остальные запросы ждут слот и чаще всего быстро получают `503`, не доходя до сервиса.
5. Это подтверждается распределением ошибок: `503` значительно больше, чем `504`.
6. Память и CPU шлюза остаются стабильными, значит очередь не раздувает процесс.

Поведение является корректной защитой: шлюз отказывает избыточным запросам к деградировавшему сервису, чтобы сохранить работоспособность остальных маршрутов.

## 9. Ответы на вопросы из задания

### Вопрос 1

> 1000 RPS, downstream отвечает 10 секунд. Сколько запросов будет одновременно в полёте?

По закону Литтла:

```text
L = λ * W
L = 1000 RPS * 10 s
L = 10000 запросов
```

Без защиты в полёте было бы около 10000 запросов.

В реализации:

```text
total_timeout = 1s
L = 1000 RPS * 1s = 1000 запросов
```

Дополнительно:

```text
max_concurrency = 100
```

Поэтому реально к сервису одновременно уходит не более 100 запросов. Остальные либо быстро получают `503` от семафора, либо не создают лишнего давления на сервис.

### Вопрос 2

> Где именно образуется очередь?

Основная очередь образуется в семафоре `asyncio.Semaphore` для конкретного сервиса.

Порядок прохождения запроса:

1. запрос приходит в шлюз;
2. проверяется `circuit breaker`;
3. запрашивается слот в семафоре сервиса;
4. если слот получен, запрос уходит через общий `httpx`-пул в сервис;
5. если слот не получен за `LIMITER_TIMEOUT_MS`, запрос завершается с `503`.

Очередь в пуле `httpx` и в event loop теоретически возможна, но в прогоне до неё не доходило: семафор отсекал лишние запросы раньше.

Индикатор — распределение ошибок `503` и `504`:

- `503` означает переполнение очереди семафора;
- `504` означает, что запрос попал в сервис, но не успел получить ответ за таймаут.

Во время деградации `503` было значительно больше, чем `504`, значит узким местом был именно семафор.

### Вопрос 3

> Что изменится при таймауте в 1 секунду с числом запросов в полёте и с error rate?

При времени ответа сервиса 10 секунд и таймауте 1 секунда:

```text
L = 1000 RPS * 1s = 1000 запросов
```

Число запросов в полёте снижается с примерно 10000 до примерно 1000.

Если дополнительно действует `max_concurrency=100`, фактически выполняемых запросов становится не больше 100.

Ошибка по больному сервису становится почти 100%, так как сервис не успевает ответить за 1 секунду. При этом здоровые маршруты продолжают работать.

Именно такая картина наблюдалась в деградационном прогоне.

## 10. Что не успел реализовать

Планировалось: гистограмма латентности по маршрутам, счётчики кодов ответов и таймаутов, но были проблемы с интеграцией

### Как было бы сделано

- Библиотека: `prometheus_client`.
- Три метрики:
  - `Histogram` латентности с лейблами `service`, `method`, `status`;
  - `Counter` кодов ответов;
  - `Counter` таймаутов с типом (`connect` / `read` / `total`).
- Замер времени — в `proxy_request` до и после вызова сервиса.
- Инкремент счётчиков — в обработчиках исключений при таймаутах.
- Эндпоинт `GET /metrics` через `generate_latest()`.
- Визуализация — в Grafana: p95 по маршрутам, доля 5xx, источники таймаутов.
